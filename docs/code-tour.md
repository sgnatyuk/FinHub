# Как читать код FinHub

Маршрут по коду для PHP/Laravel-разработчика, который хочет понимать каждую строку
и каждое решение. Идём снизу вверх: от пакетов без зависимостей к пакетам, которые
их используют. На каждом шаге есть **что смотреть**, **зачем так сделано**,
**как было бы в Laravel** и **упражнения**.

Весь маршрут — примерно 6–8 часов, удобно разбить на 4 вечера:

| Вечер | Шаги | О чём |
| --- | --- | --- |
| 1 | 0–2 | инструменты, модуль, `money`, `user` |
| 2 | 3–4 | `hub`, `category`: сервисы, интерфейсы, права |
| 3 | 5–6 | `expense`, `stats`: сценарии, частичное обновление, дженерики |
| 4 | 7–9 | тесты, сквозные темы, упражнения |

---

## Шаг 0. Подготовка

Поставьте в VS Code расширение **Go** (оно ставит `gopls`). Дальше пригодится:

| Действие | Как |
| --- | --- |
| Перейти к определению | F12 |
| Кто реализует интерфейс | Ctrl+F12 на имени интерфейса — увидите `hub.Service` и fakes из тестов |
| Кто вызывает функцию | Shift+Alt+H (Call Hierarchy) |
| Документация пакета в терминале | `go doc ./internal/expense` и `go doc ./internal/expense Service.Record` |
| Все тесты с выводом | `go test -v ./...` |
| Один тест | `go test -run 'TestUpdate/owner' ./internal/expense` |
| Покрытие | `go test -cover ./...`, подробно: `go test -coverprofile=c.out ./... && go tool cover -html=c.out` |

Правило на весь маршрут: **читайте тест рядом с кодом**. Тест — это готовый пример
вызова и список граничных случаев, которые автор считал важными.

## Шаг 1. Карта пакетов

Кто кого импортирует:

```
money, user   — ни от кого не зависят
hub           → money, user
category      → hub, user
expense       → category, hub, money, user
stats         → expense, category, hub, money, user
```

Что важно:

- **Граф без циклов, и это требование компилятора.** Если `hub` импортирует `category`,
  а `category` импортирует `hub`, программа не соберётся. В PHP автозагрузчику всё равно,
  в Go циклический импорт — ошибка. Поэтому заранее решаем, кто от кого зависит.
  Пример последствий — в шаге 4 (`CreateStarter`).
- **Пакеты нарезаны по фичам, а не по слоям.** В Laravel было бы `app/Models/Expense.php`,
  `app/Services/ExpenseService.php`, `app/Repositories/...`. Здесь всё про траты лежит
  в `internal/expense`. Имя пакета — часть имени: снаружи пишем `expense.Service`,
  `expense.New`, поэтому сами типы называются коротко (`Service`, а не `ExpenseService`).
- **`internal/`** — специальное имя: импортировать эти пакеты можно только изнутри модуля.
  Это граница «публичного API», которого у нас нет.
- **В ядре нет ни строчки про SQL, HTTP или Telegram.** Нужное от хранилища описано
  интерфейсами `Repository`, а реализовывать их будет пакет `postgres`.

`go.mod` — аналог `composer.json`: путь модуля (`github.com/sgnatyuk/FinHub`) становится
префиксом всех импортов, `go 1.24` — минимальная версия языка. Внешних зависимостей
пока нет, поэтому нет и `go.sum` (аналог `composer.lock`).

## Шаг 2. `money` и `user` — значения

Файлы: `internal/money/money.go`, `internal/money/money_test.go`, `internal/user/user.go`.

### Что смотреть в `money.go` сверху вниз

1. **Комментарий пакета** `// Package money ...` прямо над `package money`. Это godoc:
   его покажет `go doc` и pkg.go.dev. Принято писать его в одном файле пакета.
2. **`type Currency string`** — новый тип на основе строки. `Currency` и `string` — разные типы:
   функция, которая ждёт `Currency`, не примет произвольную строку без явного
   преобразования `Currency(s)`. Это дешёвая защита от перепутанных аргументов.
3. **Блок `const`** с `RUB` и `USD` — так в Go делают перечисления (enum в языке нет).
4. **Sentinel-ошибки** `var ErrInvalidCurrency = errors.New(...)`. Это переменные-маркеры:
   вызывающий код проверяет `errors.Is(err, money.ErrInvalidCurrency)`. Аналог своего класса
   исключения, но без `throw`: ошибка возвращается последним результатом функции.
   Текст начинается с маленькой буквы и без точки — так принято, потому что ошибки
   склеиваются в цепочку `record expense: money: invalid currency`.
5. **`type Money struct { amount int64; currency Currency }`** — поля с маленькой буквы,
   то есть **неэкспортируемые**. Снаружи пакета их нельзя ни прочитать, ни записать напрямую,
   только через `New`/`Parse` и методы `Amount()`, `Currency()`. Так гарантируется,
   что у созданного через `New` значения корректная валюта. В PHP аналог — `private`
   свойства + геттеры, но в Go видимость определяется регистром первой буквы, а граница —
   пакет, а не класс.
6. **`New` возвращает `Money`, а не `*Money`.** Money маленькое и неизменяемое, его дёшево
   копировать, как `int`. Указатель нужен, когда объект большой или его надо менять
   на месте (как `*Expense` дальше).
7. **`Parse`** — разбор пользовательского ввода `"123,45"`. Обратите внимание:
   - `strings.Cut` делит строку по первому разделителю и сразу сообщает, был ли он;
   - каждая ошибка оборачивается: `fmt.Errorf("%w: %q", ErrInvalidAmount, s)`.
     `%w` сохраняет исходную ошибку внутри новой (для `errors.Is`), `%q` печатает строку
     в кавычках, чтобы были видны пробелы;
   - явная проверка переполнения `units > (math.MaxInt64-cents)/100`. В PHP int тихо
     превратился бы во float; в Go int64 тихо «перекрутится» в отрицательное число.
     Поэтому для денег переполнение проверяется руками;
   - проверка на `"--5"`: `strconv.ParseInt` сам понимает знак, поэтому после того,
     как мы срезали один минус, второй нужно запретить явно.
8. **Методы с получателем-значением** `func (m Money) Amount() int64`. Получатель — это
   «`$this`», объявленный явно. Значение (а не указатель) — потому что методы ничего не меняют.
9. **`Add`** возвращает новое значение и ошибку. Неизменяемость: `a.Add(b)` не трогает `a`.
10. **`String()`** — реализация интерфейса `fmt.Stringer`. Никакого `implements`: у типа есть
    метод `String() string`, значит `fmt.Println(m)` напечатает `123.45 RUB`.
    Это первый пример неявной реализации интерфейсов — главная идея шагов 3–5.
11. **`validCurrency` со `switch`** — неэкспортируемый помощник. В Go `switch` не проваливается
    в следующий `case` (break не нужен), а в одном `case` можно перечислить несколько значений.

### Почему деньги в копейках

`0.1 + 0.2 != 0.3` во float. Любой бухгалтерский код хранит минимальные единицы целым
числом. В Laravel обычно `decimal(12,2)` в БД и строки/BCMath в PHP; здесь — `int64`.

### `user.go`

`type ID int64`. Тот же приём, что с `Currency`: `user.ID`, `hub.ID`, `category.ID` — разные
типы, хотя внутри все `int64`. Перепутать `hub.ID` и `user.ID` при вызове
`Member(ctx, hubID, userID)` компилятор не даст.

### Тесты `money_test.go`

- `package money_test` (с суффиксом `_test`) — **внешний тестовый пакет**. Тест видит только
  экспортированное, как настоящий пользователь пакета. Так тестируется поведение, а не
  внутренности.
- `TestParse` — **табличный тест**: срез анонимных структур `{in, want, wantErr}` и цикл
  с `t.Run(tt.in, ...)`. Каждая строка — отдельный подтест с именем, его можно запустить
  отдельно. Добавить случай — одна строка. Это главный стиль тестов в Go.
- `errors.Is(err, tt.wantErr)` работает и для `nil`: `errors.Is(nil, nil) == true`.
  Поэтому одна строка проверяет и «ошибки быть не должно», и «должна быть именно эта».
- `mustNew` с `t.Helper()` — при падении Go укажет на строку теста, а не на строку хелпера.
- `t.Fatalf` останавливает подтест, `t.Errorf` — отмечает провал и продолжает.

### Упражнения

1. Добавьте валюту `EUR`. Сколько мест пришлось поменять? Какие тесты упали и почему?
2. Почему `Money{}` (нулевое значение) — валидный Go, но невалидная сумма? Что вернёт
   `Money{}.String()`?
3. Напишите `func (m Money) Neg() Money` и тест к нему. Есть ли граничный случай с `math.MinInt64`?

## Шаг 3. `hub` — первая «сущность» и первый сервис

Файлы: `internal/hub/hub.go`, `service.go`, `service_test.go`.

### `hub.go`

- **`type Role string` + константы** — тот же паттерн enum.
- **`Hub` и `Member` — обычные структуры с экспортированными полями.** Никаких `save()`,
  `find()`, отношений и магических атрибутов. Это главное отличие от Eloquent:
  сущность — это данные и правила, а не «объект, который умеет ходить в БД».
- **`func (m Member) IsOwner() bool`** — маленький метод вместо `m.Role == RoleOwner`,
  разбросанного по коду. Если появится роль «со-владелец», меняется одно место.
- **`New(name, now)`** — конструктор проверяет инварианты (имя не пустое, не длиннее 64 рун).
  `utf8.RuneCountInString`, а не `len`: `len("Семья")` равно 10 байтам, а не 5 символам.
  Строки в Go — это байты в UTF-8, в PHP та же история с `strlen` vs `mb_strlen`.
- **`now` передаётся параметром**, а не вызывается `time.Now()` внутри. Функция без скрытых
  зависимостей — её легко тестировать. Аналог `Carbon::setTestNow`, но без глобального состояния.
- **`Location()`** превращает строку `"Europe/Moscow"` в `*time.Location`. В хабе храним
  строку, потому что её легко положить в БД.

### `service.go`

- **`type Repository interface`** — список того, что сервису нужно от хранилища.
  Объявлен **здесь**, в пакете, который им пользуется. В Laravel интерфейс обычно лежит
  рядом с реализацией и биндится в `ServiceProvider`; в Go реализация (будущий
  `postgres.HubRepo`) ничего не знает об интерфейсе и просто имеет нужные методы.
- **Комментарии над методами интерфейса — это контракт:** какие ошибки возвращать
  (`ErrNotMember`, `ErrAlreadyMember`). Реализация обязана им следовать, тесты сервиса
  на это опираются.
- **`type Service struct { repo Repository; now func() time.Time }`** — зависимости хранятся
  в неэкспортируемых полях. `now` — функция как значение; в проде это `time.Now`.
- **`NewService(repo Repository) *Service`** — правило *accept interfaces, return structs*:
  принимаем интерфейс (можно подсунуть fake), возвращаем конкретный тип (вызывающему
  доступны все методы, документация читается).
- **Методы на `*Service`** (указатель). Сервис не копируется при каждом вызове,
  и все методы набора одинаковые — так принято, если хоть одному методу нужен указатель
  или структура не крошечная.
- **`ctx context.Context` первым аргументом** у всего, что может ходить в сеть или БД.
  Через ctx приходят отмена и таймауты (клиент закрыл соединение — запрос в БД прервётся).
  Через ctx **не** передают зависимости и «текущего пользователя».
- **`AddMember(ctx, actor, hubID, newUser)`** — кто действует, передаётся явно. Вместо
  `Auth::user()` и Policy проверка прав — первые строки метода (`requireOwner`).
- **`requireOwner`** — общий кусок, вынесенный в неэкспортируемый метод.
- **Ранние возвраты** `if err != nil { return err }` — «счастливый путь» идёт по левому краю,
  без вложенных `else`. Сначала многословно, потом начинаешь читать это глазами за секунду.

### `service_test.go`

- **`memRepo`** — рукописная in-memory реализация `Repository`. Не мок с ожиданиями
  «метод X вызван 1 раз», а маленькое работающее хранилище. Тесты проверяют результат
  (стал ли пользователь владельцем), а не то, какие методы дёрнул сервис. Поэтому они
  не ломаются при рефакторинге.
- `TestAddMember` — подтесты идут по порядку и используют общее состояние. Это сознательное
  исключение (там есть комментарий), обычно подтесты независимы.

### Упражнения

1. Найдите все места, где проверяется `IsOwner()`. Что поменять, чтобы владельцев могло быть двое?
2. Почему `Repository.Create` принимает `owner` и сохраняет хаб и участника «атомарно»?
   Что случится, если хаб сохранится, а участник — нет?
3. Добавьте `RemoveMember` (только владелец, нельзя удалить себя) с табличным тестом.

## Шаг 4. `category` — интерфейсы потребителя и границы пакетов

Файлы: `internal/category/category.go`, `service.go`, `service_test.go`.

### Что нового по сравнению с `hub`

- **`type Members interface { Member(...) }`** — пакету категорий от хабов нужен ровно
  один метод, и он объявляет интерфейс ровно из одного метода. `hub.Service` подходит под него,
  хотя ни разу не упоминает `category`. Маленькие интерфейсы — норма в Go
  (`io.Reader` — один метод). Широкий `HubServiceInterface` на 10 методов был бы признаком
  PHP-мышления.
- **`var _ category.Members = (*hub.Service)(nil)`** в конце теста — проверка на этапе
  компиляции. Если `hub.Service` поменяет сигнатуру `Member`, тесты категорий не соберутся.
  `_` — пустой идентификатор: значение никому не нужно, важна только проверка типов.
- **Права проверяет сервис, а не репозиторий.** Репозиторий тупой: «дай категорию X в хабе Y».
  Сервис: «а состоит ли actor в хабе Y?». Так хранилище легко заменить, а правила не размазаны.
- **`Get(ctx, hubID, id)` в репозитории ищет по хабу и ID одновременно.** Подставить ID
  категории чужого хаба в свой хаб не получится — тест `TestGetFromForeignHub`.
- **`Default` — get-or-create.** Сначала ищем «Прочее», при `ErrNotFound` создаём.
  Обратите внимание на ветку `errors.Is(err, ErrDuplicateName)`: два запроса одновременно
  могут оба не найти и оба попытаться создать; второй получит ошибку уникальности из БД,
  и мы просто перечитываем. Это защита от гонки без блокировок.
- **`errors.Is(err, ErrNotFound)` vs `err == ErrNotFound`.** Используйте `errors.Is`:
  ошибка может быть обёрнута через `%w`, и `==` её не узнает.
- **`CreateStarter` и цикл импортов.** Логично, чтобы хаб при создании сам заводил категории.
  Но `category` импортирует `hub`, значит `hub` импортировать `category` не может. Решение —
  склейка в вызывающем коде: `hub.Create` → `category.CreateStarter`. В Laravel тут было бы
  событие `HubCreated` и listener; в Go предпочитают явный вызов, который видно в коде.
- **`Delete` с переносом трат делегирован репозиторию** (`Delete(ctx, hubID, id, moveTo)`):
  переназначить траты и удалить категорию нужно одной транзакцией, а транзакции — забота
  хранилища. Пакет категорий при этом не знает про траты (снова цикл: `expense` импортирует `category`).
- **`normalizeName`** вынесена из `New`, чтобы ей пользовался и `Rename`. Одна точка правды
  для правил имени.
- **`StarterNames` — `var`, а не `const`**: константами в Go могут быть только числа,
  строки и bool, срез — нет.

### Упражнения

1. Почему `SameName` — функция пакета, а не метод `Category`?
2. Что произойдёт, если вызвать `Delete` в хабе, где «Прочее» ещё нет? (Прочитайте `Delete` → `Default`.)
3. Напишите тест: переименовать категорию в «прочее» (маленькими буквами), когда «Прочее» уже есть.

## Шаг 5. `expense` — главный сценарий

Файлы: `internal/expense/errors.go`, `tag.go`, `expense.go`, `service.go` и тесты.
Читайте в этом порядке.

### `errors.go`

Все sentinel-ошибки пакета в одном месте — удобно клиентам: CLI и бот сделают
`switch { case errors.Is(err, expense.ErrInvalidAmount): ... }` и покажут человеку
понятный текст.

### `tag.go`

- **`type Tag string`** — тег как значение. Нет ID, нет таблицы в домене. Два тега равны,
  если равны строки, сравнение `==`.
- **`ParseTag`** — нормализация (обрезать, убрать `#`, нижний регистр) и проверка.
  `for _, r := range s` идёт по **рунам** (символам Unicode), а не по байтам, — поэтому
  кириллица работает. `unicode.IsLetter` знает про все алфавиты.
- **`ParseTags`** убирает дубликаты, сохраняя порядок: `map[Tag]bool` как множество
  (в Go нет отдельного типа set). `make([]Tag, 0, len(raw))` — срез нулевой длины
  с заранее выделенной ёмкостью, чтобы `append` не перевыделял память.

### `expense.go`

- **`Expense` экспортирует поля**, в отличие от `Money`. Это осознанный компромисс:
  адаптеру БД и клиентам нужно читать и заполнять поля, а инварианты при создании и
  изменении гарантирует `New`, через которую идут все пути сервиса.
- **`New` проверяет только то, что можно проверить без хранилища**: сумма > 0, длина заметки,
  число тегов, дата не в будущем. Существует ли категория — вопрос к хранилищу, это делает сервис.
- **`spentAt.IsZero()`** — нулевое значение `time.Time` означает «не указано», подставляем `now`.
  Нулевые значения как «пусто» — частый приём в Go (`""`, `0`, `nil`, `time.Time{}`).
- **Возвращает `*Expense`** — сущность изменяемая (репозиторий запишет в неё `ID`), передаём указатель.

### `service.go`

- **Три интерфейса потребителя**: `Repository`, `Categories`, `Hubs`. У `Hubs` два метода,
  потому что сервису трат нужны и валюта хаба (`Get`), и роль (`Member`).
- **`Filter`** — структура, где нулевое значение поля значит «не фильтровать». Удобно:
  `expense.Filter{AuthorID: mom}` — только траты мамы, остальное без ограничений.
- **`RecordInput`** — входные данные структурой. Восемь позиционных аргументов легко
  перепутать; структура с именованными полями читается как форма. Это аналог
  DTO/FormRequest, но без магии.
- **Порядок шагов в `Record` неслучаен:**
  1. участие в хабе и его валюта — дальше нет смысла что-то проверять для чужого;
  2. валюта суммы совпадает с валютой хаба;
  3. разбор тегов — дешёвая проверка без I/O;
  4. категория (или «Прочее») — запрос к хранилищу;
  5. теги не совпадают с именами категорий;
  6. инварианты `New`;
  7. сохранение.
  Если что-то не так, до `repo.Create` дело не доходит — тесты проверяют, что после
  ошибки в хранилище пусто.
- **Обёртка ошибок только на границе I/O**: `fmt.Errorf("record expense: %w", err)`.
  Ошибки валидации возвращаются как есть — у них уже понятный текст.
- **`UpdateInput` с указателями.** `Note *string`: `nil` — не трогать, `ptr("")` — стереть.
  Без указателя нельзя отличить «не прислали» от «прислали пустое». В Laravel это
  `$request->has('note')`. `Tags *[]string` — указатель на срез по той же причине:
  `nil`-указатель — «не трогать», указатель на пустой срез — «убрать все теги».
- **`Update` собирает новое состояние и прогоняет через `New`** — все инварианты в одном месте,
  нельзя «забыть» проверку при редактировании.
- **`getModifiable`** — общая проверка «автор или владелец» для `Update` и `Delete`.
- **`resolveCategory`** — `0` означает «Прочее». Используется и при записи, и при редактировании.
- **Короткая запись `if tags, err = ParseTags(...); err != nil`** — присваивание и проверка
  в одной строке, переменные `tags` и `err` уже объявлены выше (`=`, а не `:=`). Если
  написать `:=`, внутри `if` появились бы новые переменные, и внешний `tags` не изменился бы.
  Это классическая ловушка затенения (shadowing) — посмотрите на неё внимательно.

### Тесты `service_test.go`

- Три fake'а: `memExpenses`, `fakeCategories`, `fakeHubs`. `fakeHubs` — это `map`, у которой
  есть методы. В Go методы можно объявить у любого своего типа, не только у структуры.
- `func ptr[T any](v T) *T { return &v }` — дженерик-хелпер: в Go нельзя написать `&"строка"`
  или `&0`.
- `TestUpdate` — у каждой строки таблицы своя функция `check`: функции — обычные значения.

### Упражнения

1. Поменяйте в `Update` `if tags, err = ParseTags(...)` на `:=` и запустите `go vet ./...`. Что скажет компилятор? Что произошло бы, если бы внутренняя `tags` где-то использовалась?
2. Почему `Record` проверяет валюту до разбора тегов, а не после? Важно ли это?
3. Добавьте в `Filter` поле `MinAmount` и поддержите его в `memExpenses.List`.
4. Сейчас `Update` вызывает `hubs.Member` (в `getModifiable`) и `hubs.Get` — два запроса.
   Как бы вы это упростили? Стоит ли?

## Шаг 6. `stats` — запросы и дженерики

Файл: `internal/stats/stats.go`, `stats_test.go`.

- **Здесь нет сущностей**, только типы результатов (`CategoryTotal`, `TagTotal`, …) —
  read-модель. Считать суммы будет SQL (`GROUP BY`): тащить все траты в память ради
  суммы — антипаттерн и в Laravel (`->sum()` в запросе, а не `->get()->sum()`).
- **Фильтр переиспользуется** — `expense.Filter`. `stats` импортирует `expense`, а не наоборот.
- **`query[T any]` и `mine[T any]` — дженерики.** У трёх отчётов одинаковый каркас:
  проверить доступ → получить строки → отсортировать по сумме. Отличаются тип строки и метод
  хранилища. `T` — тип строки, `fetch` — метод репозитория, `total` — как достать сумму.
- **`s.repo.ByCategory` без скобок — method value**: метод, привязанный к конкретному `repo`,
  передаётся как обычная функция.
- **`slices.SortStableFunc` + `cmp.Compare`** — стандартная библиотека Go 1.21+.
  `Stable` сохраняет порядок строк с равными суммами, `cmp.Compare(b, a)` — по убыванию.
- **`mine` сбрасывает `f.CategoryID = 0`.** `f` передан по значению, поэтому изменение
  не видно вызывающему. Структуры в Go копируются при передаче (кроме указателей и
  «ссылочных» внутренностей — срезов, map). Подумайте, что было бы со срезом `f.Tags`.

### Упражнения

1. Перепишите `ByTag` без дженерика. Сколько кода стало? Что читается проще?
2. Что вернёт `MineByHub`, если у пользователя нет хабов? Почему `nil, nil`, а не пустой срез?
   (Подсказка: для `range` и `len` разницы нет.)

## Шаг 7. Тесты как стиль

Сводка приёмов, которые встречались на всём маршруте:

| Приём | Где посмотреть | Зачем |
| --- | --- | --- |
| Внешний тестовый пакет `xxx_test` | все `*_test.go` | тестировать публичное поведение |
| Табличные тесты + `t.Run` | `TestParse`, `TestRecord` | случаи — данные, не копипаста |
| `errors.Is` против `wantErr` | везде | одна проверка для «нет ошибки» и «нужная ошибка» |
| Рукописные fakes | `memRepo`, `fakeHubs` | проверять результат, а не вызовы |
| `t.Helper()` | `mustNew`, `rub` | правильная строка в сообщении о падении |
| Проверка интерфейса при компиляции | `var _ X = (*Y)(nil)` | сломанный контракт — ошибка сборки |
| Сообщения `got X, want Y` | везде | стандартный формат Go |

Чего здесь нет и почему: моков с ожиданиями (gomock/mockery), assert-библиотек (testify),
фабрик и сидеров. Всё это существует, но стандартного `testing` пока хватает, и вы видите,
как всё устроено, без магии.

## Шаг 8. Сквозные темы — шпаргалка

**Ошибки.** Возвращаются последним результатом. Проверяются сразу. Оборачиваются `%w`
с контекстом «что делали». Сравниваются `errors.Is` (sentinel) или `errors.As` (тип ошибки).
`panic` — только для «программа сломана», не для бизнес-ошибок.

**Значение или указатель.** Маленькое и неизменяемое (`Money`, `Tag`, `Filter`) — значение.
Изменяемая сущность (`*Expense`) или объект с зависимостями (`*Service`) — указатель.

**Нулевые значения.** У каждого типа есть «ноль»: `0`, `""`, `nil`, `time.Time{}`. Хороший
Go-код делает ноль полезным: `Filter{}` — «без фильтра», `CategoryID: 0` — «Прочее».

**Имена.** Экспорт — заглавная буква. Короткие имена в маленькой области видимости
(`e`, `c`, `h`, `tt`), описательные — для пакетов и экспортируемого API. Без `Get`
у геттеров (`Amount()`, не `GetAmount()`). Без повторения пакета (`expense.Service`,
не `expense.ExpenseService`).

**Комментарии.** Экспортируемое имя — комментарий, начинающийся с этого имени
(`// New создаёт ...`). Комментарий объясняет «зачем», а не пересказывает код.

**Форматирование.** `gofmt` решает всё, спорить о стиле не нужно. Запускайте перед коммитом.

**Внедрение зависимостей.** Нет контейнера: зависимости передаются в `NewService(...)`,
а всё собирается в `main.go`. Это сотня строк кода, зато видно, что от чего зависит.

### Laravel → Go одной таблицей

| Laravel | FinHub |
| --- | --- |
| Eloquent-модель с `save()` | struct + `Repository` |
| `app/Models`, `app/Services` | пакеты по фичам |
| `ExpenseRepositoryInterface` рядом с реализацией | маленький интерфейс у потребителя |
| ServiceProvider, автовайринг | `NewService(deps...)` в `main.go` |
| Исключения + Handler | ошибки-значения, `errors.Is` |
| `Auth::user()`, Policy | `actor user.ID` в аргументах, проверка в сервисе |
| FormRequest | `RecordInput` + `New` + сервис |
| `$request->has()` | указатели в `UpdateInput` |
| Enum / константы класса | `type Role string` + `const` |
| События и listeners | явный вызов в вызывающем коде |
| `Carbon::setTestNow` | `now func() time.Time` |
| Mockery, RefreshDatabase | рукописные fakes |
| `decimal` / BCMath | `int64` копейки |

## Шаг 9. Проверь себя

Если на все вопросы есть ответ своими словами — код понят.

1. Почему `Money` хранит поля приватно, а `Expense` — публично?
2. Где объявлен интерфейс, который реализует `hub.Service`, и почему не в пакете `hub`?
3. Что сломается, если `category` импортирует `expense`?
4. Как сервис узнаёт, что пользователь имеет право удалить трату?
5. Зачем `ctx` в каждом методе, если в fakes он не используется?
6. Чем `errors.Is(err, X)` лучше `err == X`?
7. Почему валидация суммы в `expense.New`, а проверка категории — в `Service.Record`?
8. Как в `UpdateInput` отличить «не менять теги» от «убрать все теги»?
9. Почему суммы статистики не считаются в Go-коде?
10. Что делает `var _ expense.Hubs = (*hub.Service)(nil)` и когда «срабатывает»?
