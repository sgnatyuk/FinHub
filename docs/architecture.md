# Архитектура FinHub

Как устроен проект, по каким правилам, и как по этим правилам добавлять фичи,
хранилища и клиенты, не превращая код в кашу.

## Коротко

FinHub — **порты и адаптеры** (hexagonal architecture) в облегчённом Go-варианте:

- **ядро** — бизнес-правила, оно ничего не знает о БД, CLI и Telegram;
- **порты** — маленькие интерфейсы, которые ядро объявляет для того, что ему нужно снаружи;
- **адаптеры** — реализации портов (Postgres) и клиенты, которые вызывают ядро (CLI, бот);
- **точка сборки** — `main.go`, где всё соединяется руками.

Поверх этого два Go-специфичных правила: **пакеты по фичам** и **интерфейс объявляет потребитель**.

Это та же идея, что Clean Architecture или «Laravel с сервисным слоем и репозиториями»,
но без лишних слоёв: нет отдельных пакетов `domain/`, `usecase/`, `infrastructure/`,
нет DTO на каждой границе и нет DI-контейнера.

## Картина целиком

```
┌──────────── клиенты (driving adapters) ─────────────┐
│  cmd/finhub-cli → internal/cli                      │
│  cmd/finhub-bot → internal/telegram                 │
└──────────────────────┬──────────────────────────────┘
                       │ вызывают сервисы
┌──────────────────────▼──────────────────────────────┐
│ ядро: internal/money, user, hub, category,          │
│       expense, stats                                │
│   сущности + конструкторы New (инварианты)          │
│   Service (сценарии, права)                         │
│   интерфейсы-порты: Repository, Hubs, Categories    │
└──────────────────────▲──────────────────────────────┘
                       │ реализуют порты
┌──────────────────────┴──────────────────────────────┐
│ хранилище (driven adapters): internal/postgres      │
└─────────────────────────────────────────────────────┘

main.go: создаёт pgxpool → postgres-репозитории → сервисы → клиент
```

**Правило зависимостей:** стрелки импортов идут только внутрь, к ядру. `postgres` импортирует
`expense`, чтобы знать тип `expense.Expense`, а `expense` не импортирует `postgres` никогда.
Клиенты импортируют ядро, ядро клиентов — никогда. Проверить легко:
`go list -deps ./internal/expense` не должен показывать `postgres`, `pgx`, `telegram`.

## Из чего состоит пакет фичи

На примере `internal/expense`:

| Часть | Файл | Что там | Чего там быть не должно |
| --- | --- | --- | --- |
| Сущность | `expense.go` | `type Expense struct`, `New(...)` с инвариантами | SQL, `ctx`, вызовы других сервисов |
| Значения | `tag.go` | `type Tag string`, `ParseTag` | состояние, I/O |
| Ошибки | `errors.go` | sentinel-ошибки пакета | тексты для пользователя на русском (это забота клиента) |
| Порты | `service.go` (вверху) | `Repository`, `Hubs`, `Categories` — только нужные методы | методы «на будущее» |
| Сервис | `service.go` | сценарии: `Record`, `Update`, `Delete`, проверка прав | форматирование вывода, знание о CLI/боте |
| Тесты | `*_test.go` | табличные тесты сервиса на fakes | реальная БД |

Пакет растёт — делите **по файлам**, а не по подпакетам: `service.go`, `update.go`, `filter.go`.
В Go пакет — это папка, а не файл, и десять файлов в одном пакете — нормально.

## Где живёт какое правило

Главный вопрос при добавлении любой логики. Таблица-шпаргалка:

| Правило | Куда | Пример |
| --- | --- | --- |
| Можно проверить по самим данным | конструктор `New` сущности или значения | сумма > 0, тег без пробелов |
| Нужны данные из хранилища или другого пакета | метод `Service` | категория существует в этом хабе |
| Кто имеет право | метод `Service`, первыми строками | только владелец переименовывает категорию |
| Атомарность нескольких записей | метод `Repository`, одна транзакция | удалить категорию + перенести траты |
| Уникальность, ссылочная целостность | ограничение в БД + sentinel-ошибка из адаптера | `ErrDuplicateName` из unique index |
| Подсчёт по многим записям | SQL в адаптере, порт в `stats` | суммы по категориям |
| Как показать человеку | клиент | «Сумма должна быть больше нуля» |
| Разбор ввода конкретного клиента | клиент | `/add 250 такси #работа` → `RecordInput` |
| Общий разбор ввода для всех клиентов | ядро | `money.Parse`, `expense.ParseTag` |

## Рецепт: новая фича

Пример — **бюджет хаба на месяц** из `roadmap.md`.

**1. Решите, новая это фича или часть существующей.** Есть ли у бюджета свой жизненный
цикл и свои правила? Да: создать, поменять, узнать остаток. Значит, новый пакет `internal/budget`.
Если бы это было одно поле хаба, оно легло бы в `hub`.

**2. Определите зависимости пакета и проверьте, что не будет цикла.** `budget` нужны
`hub.ID`, `money.Money`, права (`hub.Member`) и сумма трат за месяц (из `stats` или
отдельный порт). Значит, `budget` → `hub`, `money`, `user`. Никто из них не должен импортировать
`budget`. Если хочется, чтобы `stats` показывал остаток, то `stats` → `budget`, а не наоборот.

**3. Сущность и инварианты:**

```go
package budget

type Budget struct {
	HubID  hub.ID
	Month  time.Time // первое число месяца в поясе хаба
	Amount money.Money
}

func New(hubID hub.ID, month time.Time, amount money.Money) (*Budget, error) // amount > 0
```

**4. Порты — только то, что нужно сервису:**

```go
type Repository interface {
	Set(ctx context.Context, b *Budget) error // upsert
	Get(ctx context.Context, hubID hub.ID, month time.Time) (*Budget, error) // ErrNotFound
}

type Hubs interface {
	Get(ctx context.Context, actor user.ID, hubID hub.ID) (*hub.Hub, error)
	Member(ctx context.Context, hubID hub.ID, userID user.ID) (*hub.Member, error)
}

type Spending interface {
	Total(ctx context.Context, hubID hub.ID, f expense.Filter) (money.Money, error)
}
```

**5. Сервис со сценариями и правами:** `Set` (только владелец, валюта хаба),
`Remaining(ctx, actor, hubID, month)` (любой участник).

**6. Тесты сервиса на fakes** — до любой БД. Табличный тест на права, валюту и остаток.

**7. Адаптер:** миграция `budgets`, `postgres.BudgetRepo`, интеграционный тест.

**8. Клиенты:** команда `/budget 80000`, строка «осталось 12 300 ₽» в `/stats`.

**9. Сборка в `main.go`:** `budget.NewService(postgres.NewBudgetRepo(pool), hubs, spending)`.

**10. Документация:** строка в `decisions.md` (почему так), отметка в `roadmap.md`.

Порядок важен: шаги 3–6 не требуют ни БД, ни клиента, поэтому правила проверены тестами
до того, как появится первая таблица.

## Рецепт: новое хранилище или новый клиент

**Хранилище.** Новый пакет-адаптер реализует существующие интерфейсы `Repository`.
Ядро не меняется. Чек-лист:

- методы возвращают sentinel-ошибки ядра (`expense.ErrNotFound`, а не `pgx.ErrNoRows`):
  адаптер переводит ошибки своей технологии на язык ядра;
- `ctx` прокидывается во все запросы;
- проверка `var _ expense.Repository = (*ExpenseRepo)(nil)` в коде адаптера;
- интеграционные тесты против настоящей базы (Docker), а не моков SQL.

**Клиент.** Клиент — это тонкий слой: разобрать ввод → вызвать сервис → показать результат
или ошибку. Чек-лист:

- никаких правил домена в клиенте; захотелось написать `if amount <= 0` — правило уже есть в ядре,
  обработайте `expense.ErrInvalidAmount`;
- перевод ошибок в текст для человека через `errors.Is` в одном месте клиента;
- клиент сам решает, *кто* действует (`actor`) и *где* (`hubID`): CLI — из сессии,
  бот — из chat_id. Ядру это неважно.

## Сценарии через несколько фич

Иногда одно действие пользователя задевает несколько пакетов. Например, регистрация:
создать пользователя → личный хаб → стартовые категории.

Порядок выбора, от простого к сложному:

1. **Вызвать сервисы подряд в клиенте**, если сценарий нужен одному клиенту.
2. **Вынести в отдельный пакет сценария**, когда он нужен двум клиентам, например
   `internal/onboarding` с `Register(ctx, name)`. Он импортирует `user`, `hub`, `category`;
   его не импортирует никто из ядра. Так сценарий не дублируется в CLI и боте, а циклов нет.
3. **Транзакция на несколько репозиториев.** Если шаги должны откатиться вместе, порт
   получает метод «сделай всё в транзакции», например `Repository.Create(h, owner)` в `hub`
   или общий `postgres.Tx(ctx, func(tx) error)`, которым пользуется пакет сценария.
   Начинайте с первого варианта: один метод репозитория на одну атомарную операцию.
4. **События** (`ExpenseRecorded` → уведомление в бот) — только когда реакций много
   и они не должны тормозить основной сценарий. До этого прямой вызов проще и понятнее.

## Как понять, что пора что-то менять

| Сигнал | Что делать |
| --- | --- |
| Пакет импортирует пакет, который импортирует его (ошибка компиляции) | вынести общее вниз или сценарий наверх, в отдельный пакет |
| В интерфейсе потребителя больше 4–5 методов | возможно, пакет делает слишком много, разделить порт или сервис |
| Один и тот же разбор ввода в CLI и боте | перенести функцию в ядро (`ParseX`) |
| `if role == ...` в нескольких сервисах | метод на `hub.Member` (`CanEditCategories()`) |
| Сервис-метод длиннее экрана | вынести шаги в неэкспортируемые методы, как `resolveCategory` |
| Fake в тестах повторяется в трёх пакетах | нормально до поры; потом общий `internal/fakes`, но только для тестов |
| Хочется пакет `common` / `utils` | нет: найдите, чьё это поведение, и положите туда |

## Анти-паттерны, от которых мы ушли

- **Active Record.** Сущность, которая сама сохраняется, тянет за собой БД в каждый тест
  и в каждую функцию.
- **Один большой интерфейс рядом с реализацией** (`ExpenseRepositoryInterface` на 15 методов).
  Потребители зависят от того, что им не нужно; fakes разрастаются.
- **Глобальное состояние**: `Auth::user()`, фасады, синглтоны. Зависимости становятся невидимыми,
  тесты — хрупкими.
- **DI-контейнер и автовайринг.** В Go граф зависимостей пишется в `main.go` руками,
  ошибки ловит компилятор, а не рантайм.
- **Слои ради слоёв**: DTO → Entity → Model → Resource на каждой границе. Здесь сущность ядра
  сама проходит через границы, а отдельный тип заводится только когда форма данных
  реально другая (`RecordInput`, `CategoryTotal`).
- **Логика в клиенте.** Всё, что должно одинаково работать в CLI и боте, — в ядре.

## Тестовая пирамида

| Уровень | Что | Где | Скорость |
| --- | --- | --- | --- |
| Юнит | конструкторы, значения, сервисы на fakes | `internal/<feature>/*_test.go` | миллисекунды, большинство тестов |
| Интеграционный | адаптер против настоящего Postgres | `internal/postgres/*_test.go`, Docker | секунды |
| Сквозной | клиент целиком: команда → БД → вывод | несколько тестов на клиент | секунды |

Правила проверяются на нижнем уровне. Интеграционные тесты проверяют только то,
что адаптер честно выполняет контракт порта: SQL, транзакции, перевод ошибок.

## Что ещё появится и куда

| Что | Куда |
| --- | --- |
| Конфигурация (DSN, токен бота) | `internal/config`, читается в `main.go`, в ядро не попадает |
| Логирование | `log/slog`, логгер передаётся в адаптеры и клиенты; ядро возвращает ошибки, а не пишет логи |
| Миграции | `internal/postgres/migrations`, goose |
| Аутентификация CLI | `internal/auth`: токены и сессии сводятся к `user.ID` |
| Приглашения в хаб | `hub` (код приглашения как значение) + клиенты |
